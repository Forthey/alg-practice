# Algorithm practice

Задачи сгруппированы по источнику, сложности или номеру занятия. Состав сборки
задаётся в [`tasks.yaml`](tasks.yaml). Требуются CMake 3.22+, компилятор C++23
и Rust 1.86+ для менеджера. GoogleTest скачивается CMake при первой настройке
сборки с тестовыми задачами; Cargo скачивает зависимости менеджера.

```sh
cargo build --manifest-path tasks_manager/Cargo.toml --locked
cargo run --manifest-path tasks_manager/Cargo.toml -- sync tasks.yaml
cargo run --manifest-path tasks_manager/Cargo.toml -- check tasks.yaml
cmake -S . -B build -G Ninja
cmake --build build --parallel
ctest --test-dir build --output-on-failure
```

Если старая директория `build` настроена на другой генератор или компилятор,
выберите новую, например `build/yaml`. Для выбора компилятора используйте
`-DCMAKE_CXX_COMPILER=...` при первой конфигурации. На Windows при отсутствии
Cargo в PATH можно вызвать `& "$env:USERPROFILE/.cargo/bin/cargo.exe"` из PowerShell.

Для удобного запуска из корня проекта соберите менеджер PowerShell-скриптом:

```powershell
.\tasks_manager\build.ps1
.\tasks_manager.exe sync
.\tasks_manager.exe check
```

Скрипт собирает release-версию и копирует готовый executable в корень проекта.
Для debug-сборки используйте `-Profile debug`. Скрипт можно вызывать из любого
каталога; он находит Cargo в PATH или стандартном каталоге Rust на Windows.
Обычный `cargo build` сохраняет прежнее поведение. Корневой executable исключён
из Git. В PowerShell на Linux/macOS имя копии — `tasks-manager`.

В Linux используйте Bash-версию (нужны Bash, Rust/Cargo и Python 3):

```sh
bash tasks_manager/build.sh
./tasks-manager sync
./tasks-manager check
```

Для debug-сборки: `bash tasks_manager/build.sh debug`. Скрипт можно запускать
из любого каталога. Он находит Cargo в PATH или `${CARGO_HOME:-$HOME/.cargo}/bin`,
а путь к бинарнику читает из JSON-вывода Cargo через стандартную библиотеку Python.
При ошибке сборки существующий бинарник в корне остаётся нетронутым.

## Добавление задачи

```yaml
version: 1
tasks:
  leetcode:
    easy:
      new-task:
        include_tests: true
        source_files: [solution.cpp]
```

Вложенные ключи задают путь `leetcode/easy/new-task`. `include_tests` обязателен:
`true` выбирает `tests.cpp` и GoogleTest, `false` — `main.cpp`. Не перечисляйте
эти файлы в `source_files`. Список содержит только дополнительные `.cpp`, `.cc`
или `.cxx` относительно каталога задачи; заголовки перечислять не требуется.
Для начала с одного шаблона опустите `source_files`. Для каждого указанного
исходника `sync` создаёт недостающие файлы пары: `solution.cpp` с
`#include "solution.h"` и `solution.h` с `#pragma once`. Создание независимо:
если один файл уже существует, его содержимое сохраняется, создаётся только второй.
Для `.cc` и `.cxx` действует то же правило; расширение заголовка всегда `.h`.
Вложенные пути поддерживаются: для `helpers/search.cpp` заголовок создаётся
в `helpers/search.h`, а исходник включает `"search.h"`.

Вызов `sync` создаст каталог и нужный шаблон, затем обновит `tasks.cmake`.
Новый GoogleTest-шаблон содержит параметризованный тест с `GTEST_SKIP()`:
добавьте примеры, вызов решения и `EXPECT_EQ`, убрав пропуск.
Существующие файлы никогда не перезаписываются. Затем снова выполните сборку.
Если CMake ещё не настроен, сначала выполните команду конфигурации.

## Синхронизация и ошибки

- `sync [manifest]` создаёт отсутствующие шаблоны точки входа, исходников и
  заголовков, проверяет задачи и записывает реестр допустимых целей.
  По умолчанию используется `tasks.yaml`.
- `check [manifest]` ничего не записывает; проверяет обязательные файлы и
  актуальность `tasks.cmake`, наличие перечисленных исходников и их парных `.h`.
- Относительные пути разрешаются от каталога манифеста, независимо от места запуска.
- Одновременное наличие `main.cpp` и `tests.cpp`, наличие противоположного файла
  или некорректный путь исходника/заголовка исключает задачу из реестра при `sync`.
  Остальные задачи синхронизируются; команда возвращает код 1.
- Ошибки YAML или схемы прерывают операцию до записи файлов. Ошибки записи также
  прерывают операцию; уже созданные шаблоны остаются, реестр заменяется целиком.
- Удаление записи из YAML удаляет только объявление цели, исходники остаются.
- Повторный `sync` без изменений не переписывает файлы. Вывод содержит CREATE,
  ADD, UPDATE, REMOVE и итоговые счётчики. `NO_COLOR=1` отключает цвет.
- Код 0 означает успех; 1 — ошибки проверки/синхронизации; 2 — неверные аргументы CLI.

Ключи каталогов — строки; числовые имена заключайте в кавычки (`"01"`, `"02"`).
Используйте явные YAML-отображения и имена из ASCII-букв, цифр, `_`, `-`, `.`.
Нельзя использовать `.`/`..`, скрытые имена, завершающую точку, Windows device names,
абсолютные пути, обратные слеши и выходящие за корень символические ссылки.
Корневые `build`, `tasks_manager`, `cmake`, `utility`, `docs` зарезервированы.
Имена целей CMake/GoogleTest (`all`, `test`, `gtest` и другие служебные цели)
также зарезервированы; внутри группы имя `all` допустимо, например `examples/all`.
То же относится к именам `NAME`, `DIRECTORY`, `INCLUDE_TESTS`, `SOURCES`,
совпадающим с ключевыми словами CMake-хелпера.
Дубли ключей, неизвестные поля, коллизии имён без учёта регистра и коллизии
имён целей (путь с заменой `/` на `__`) диагностируются до записи файлов.

[`tasks.cmake`](tasks.cmake) генерируется полностью и хранится в Git;
не редактируйте его вручную. Общая сборочная функция находится в
[`cmake/AddTask.cmake`](cmake/AddTask.cmake). CMake не запускает Rust автоматически:
после изменения манифеста сначала выполните `sync`. `check` удобно использовать в CI.
